# 100条新用例 + 重复采样：Builder v1/v2

2026-09-10。100条不同用例、10个场景族；每条各测v1/v2，另对10条哨兵各重复两次，总240次真实DeepSeek请求。提示词冻结，全程未修改v1/v2。以下主表只统计repeat0的100条/版本。

| 结果类别 | v1 | v2 |
|---|---:|---:|
| 符合严格预设的retrieve | 47 | 70 |
| 合理wait（歧义/不支持/partial去重） | 25 | 21 |
| 有查询机会但保守wait | 16 | 1 |
| 核心字段正确、排序/limit变体待复核 | 12 | 4 |
| partial重复生成相同query | 0 | 4 |
| 明确实体/显式约束错误 | 0 | 0 |
| API/解析错误 | 0 | 0 |

原summary中v2的4条`unjustified_retrieve`经逐条核对，全部属于duplicate_phase。将返回query与previous_queries用Query.parse规范化比较，四条完全相等。因此这里解释为多余查询，不冒充错误实体或危险错误复用。未重新调用模型、未改原始记录或按结果调prompt。原记录里的宽泛类别保留，报告给出审计解释。

重点场景：
- 最近实体追问：v1正确3/10、wait7/10；v2正确10/10。
- 长历史中的最新实体：v1正确2/10、wait8/10；v2正确9/10、wait1/10。
- 歧义10条、不支持业务10条：两版都wait，没有在这些样例中擅猜。
- 明确多条件10条、约束修订10条：两版均满足预设。
- partial重复查询5条：v1全部wait，v2只有1条wait、4条重复retrieve。final重复输入的另外5条两版都正确retrieve。

不能简单称v2“更安全”：本轮主要收益是减少保守跳过，代价是更多partial冗余query输出（不等于新增SQL请求）；没有足够证据证明危险错误率改善。16条排序/limit变体尚未逐例用数据证明结果覆盖等价，不能归入已验证安全。

重复采样：每族首条在每个版本下共3次；10×2组结果类别均一致。只检查类别一致性，不等于JSON逐字相同或全分布稳定。总240次没有API/契约错误。两并发、每请求独立HTTP client，延迟中位数v1约1093ms、v2约1109ms，不与之前共享client单轮实验直接比较。

数据性质：AI编写和只读审查的开发诊断，很多用例是同一场景族的实体/措辞替换；不是100种独立语义机制，也不是公司真实语料、跨schema测试或严格holdout。不能从本轮零明确错误推导生产零风险。旧10条样例不计入分母。Answerer与真实STT未参与，因此没有证明wait之后的整链路答案正确。

保留结论：默认仍v1，v2保持显式可选；用户接受wait跳过Checker。下一步若继续，应补公司场景的独立标注输入与更多容易误指代/约束冲突的用例，而不是仅扩大商品名排列或继续追着这100条调prompt。

证据：cases.json完整输入/标签；prompts.json实际system指令；results.jsonl全部240次原始返回与API metrics；summary.json按族汇总。方法与评分细节见METHOD.md。复现使用`builder_expanded_eval.py`，避免覆盖现有输出目录。
