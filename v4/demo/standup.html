WHY / LIVEKIT RETRIEVAL EXPERIMENT

Valid JSON can still be the wrong query.

A concrete failure changed what we need to validate.

Request: “Keep the category, but only packages containing 12 units.”

v2 · rejected

{ category_id: 4,
quantity_per_unit: "12", limit: 5 }

The unsupported field is rejected by the parser.

v3 · accepted syntax, lost meaning

{ category_id: 4, limit: 5 }

The package condition disappears. Execution is possible; the request is not preserved.

Builder: request fidelityChecker: candidate applicabilityAnswerer: evidence sufficiency

This is a Builder failure, not a measured Checker false positive. Matching two queries cannot restore a condition that both omitted. Defaults remain unchanged.

WHAT NEXT / LIVEKIT RETRIEVAL EXPERIMENT

Move the experiment into the real stack.

Proposed integration plan — company implementation has not started here.

  1. Inspect and preserveRead company repository rules, SDK version, STT event semantics, tools and current retrieval baseline.
  2. Adapt the domain boundaryReplace Query + schema + Builder instructions + retriever together. Preserve provider tools and streaming TTS.
  3. Validate before servingAuthorized recordings and labeled short / long / follow-up negatives; test cancellation, committed history and fallbacks.
  4. Enable with a rollback pathFeature flag, bounded shadow traffic and controlled trials. Measure wrong reuse, answer quality, extra calls and useful-answer latency.

Standup ask: agree on a small target-domain evaluation set and the retrieval interface. Do not promote a prompt or similarity threshold from these developer-authored cases.
